# Naming conventions

## Три разных имени

Для одного понятия допускаются три технических представления имени, но их смысл должен совпадать.

### 1. Display / semantic Name

Название, которое видит преподаватель на диаграмме.

Для Use Case — русская процессная формулировка:

`Настроить сценарий развития`.

Методичка требует, чтобы Use Case назывался как процесс, а не данные/событие [METHOD: P0092].

### 2. Diagram/internal identifier

Короткое стабильное имя диаграммы, обычно на английском:

`ScenarioConfiguration`.

Методичка отдельно рекомендует английские имена Activity Diagram из-за ограничений инструментов [METHOD: P0216–P0217]. Мы распространяем это соглашение на технические имена диаграмм.

### 3. Registry/file id

Machine-friendly identifier:

`scenario_configuration`.

Он используется только в наших JSON/скриптах и не обязан отображаться в StarUML.

## Правила

- Не создавать синонимы для одного понятия без необходимости.
- `Scenario`, `GenerationScenario`, «Сценарий развития» не должны существовать как три независимые сущности, если предметно это одно и то же.
- Множественное число/единственное число выбирать осознанно.
- Use Case формулировать глагольной/процессной фразой.
- Entity Class обычно именуется существительным.
- Control Class именуется по ответственности, а не по UI-экрану.
- Component именуется архитектурной ролью.
- Deployment service использует фактическое имя среды/сервиса, если оно стабильно.

## GUID

GUID — идентичность, Name — отображаемое имя.

Обычное переименование не создаёт новый GUID.

Новый GUID нужен только новой semantic сущности.

## Legacy lending GUID

На первом этапе часть GUID была сохранена из lending-шаблона, потому что Urban Development модель строилась заменой semantic contents внутри проверенной структуры.

Это допустимо внутри отдельного проекта: GUID не обязаны быть глобально уникальными относительно другого файла.

После фиксации в нашем registry эти GUID считаются **нашими стабильными ID** и не должны пересоздаваться без причины.
