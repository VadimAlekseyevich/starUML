# 02 — Модель алгоритмов системы

Вторая работа хранится в том же каноническом StarUML 7 проекте:

`../01_functionality/urban_development_functionality.mdj`

Отдельный `.mdj` не создаётся: Use Case и поведенческие элементы должны сохранять стабильную идентичность в одном проекте.

## Покрытие Use Case первого уровня

| Use Case | Основная Activity Diagram |
|---|---|
| Создать проект | `ProjectCreation` |
| Управление исходными геоданными | `DataManagement` |
| Настроить сценарий развития | `ScenarioConfiguration` |

Это выполняет обязательное требование методички: behavior diagram для каждого Use Case основной диаграммы [METHOD: P0219–P0225; P0241–P0245].

## Декомпозиционные Activity Diagram

После повторной сверки с полной методичкой и `lending.uml` оставлены только семантически оправданные декомпозиции:

| Activity | Реализуемый вспомогательный Use Case | Вызывается из |
|---|---|---|
| `DatasetImport` | Импортировать набор геоданных | `DataManagement` |
| `DataQualityValidation` | Проверить метаданные и качество данных | `DataManagement` |
| `ScenarioValidation` | Проверить конфигурацию сценария | `ScenarioConfiguration`, `ScenarioLaunch` |
| `GenerationExecution` | Выполнить генерацию сценария | `ScenarioLaunch` |

В StarUML 7 ссылки представлены как `UMLCallBehaviorAction` с прямой ссылкой `behavior` на соответствующую `UMLActivity`. Это современный эквивалент идеи `SubactivityState` из StarUML 5 [METHOD: P0193–P0196; P0246; P0255].

Остальные действия не декомпозируются искусственно: просмотр свойств, ввод параметров, стандартная визуализация и получение готового файла достаточно точно описываются Documentation и не требуют собственной алгоритмической модели.

## GenerationExecution

Детальная Activity Diagram сохраняет канонический pipeline:

`prepare_snapshot → evaluate_constraints → suitability → zoning → roads → blocks_and_parcels → buildings → demography → infrastructure → final_validation → metrics → persist_manifest`.

Диаграмма также отражает фиксацию нарушений, критическую ошибку и безопасную отмену. В Documentation указано, что прогресс Run обновляется по этапам, а остановка проверяется Worker в безопасных точках.

## State Machine

`GenerationRunLifecycle` описывает жизненный цикл одного запуска:

`Draft → Validated → Queued → Running → Completed / Failed / Cancelled`.

State Machine используется как дополнительное представление поведения Run, а не как замена Activity Diagram [METHOD: P0279–P0298]. Дополнительные автоматы не создаются без отдельной предметной необходимости.

## Правила ветвлений и слияний

После ревизии:

- каждый `Action` имеет ровно **один входящий control flow**; альтернативные пути сначала объединяются через merge/decision [METHOD: P0274–P0275];
- guards задаются в свойствах переходов и показываются в квадратных скобках;
- для резервной ветви используется `[else]`, а не парные подписи «Да/Нет» [METHOD: P0227–P0229];
- Documentation каждого перехода объясняет, почему переход безусловный либо почему используется конкретный guard [METHOD: P0256].

## Documentation

Documentation в модели является частью курсовой, а не служебным комментарием. Для действий теперь указаны входные данные, проверяемые условия, изменение состояния и результат шага — настолько конкретно, чтобы из описания было понятно направление будущей реализации [METHOD: P0251–P0254].

## Визуальная компоновка

Композиция намеренно сделана просторной:

- ширина одной swimlane: около **460 px**;
- Action: около **320 × 72 px**;
- вертикальный шаг рядов: около **135 px**;
- длинные guard-метки ограничены по ширине и переносятся;
- обратные переходы уводятся наружу диаграммы;
- State Machine также разнесена по большему полотну.

При ручной косметической правке в StarUML лучше сохранять принцип **«больше воздуха, меньше пересечений»** и не уплотнять диаграммы ради помещения на один экран.

## Что взято из lending.uml

`lending.uml` используется как эталон масштаба и композиции, но не как формат данных StarUML 7. В нём 5 Activity и 4 Statechart; наиболее показательная `ApplyingForLoan` содержит 3 swimlane, 12 Action/Subactivity, 2 ссылки на поддеятельности, 13 псевдосостояний и 32 перехода. Это подтверждает подход с выборочной декомпозицией, а не принцип «отдельная диаграмма на каждый шаг».

Не копируются legacy-механизмы `ActivityGraph/TOP`, XPD-структура, цвета и другие особенности StarUML 5.
