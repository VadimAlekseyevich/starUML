# Шаблон текстовой спецификации Use Case

Основание: структура таблиц T0002–T0004 и правила P0165–P0174.

## Метаданные

| Поле | Содержание |
|---|---|
| Название | Каноническое имя Use Case / сценария |
| Действующие лица | Actor / worker, участвующие в сценарии |
| Краткое описание | Цель и ожидаемый результат |
| Предусловия | Что должно быть истинно до запуска |
| Постусловия | Что гарантируется после завершения |
| Приоритет | Критично / Важно / Желательно |
| Частота использования | Всегда / Часто / Иногда / Редко / Один раз |

## Основной поток

Действия нумеруются в порядке выполнения.

Ссылки на вспомогательные потоки оформляются как `S...`.

## Альтернативные потоки

Идентификатор: `A<n> [условие]`.

Альтернативный поток описывает нормальную альтернативную ветвь процесса [METHOD: P0168–P0171].

## Подпотоки

Идентификатор: `S<n>` или `S<n> [условие]`.

Безусловная ссылка соответствует include; обусловленная — extend [METHOD: P0172].

Для вложенной декомпозиции используется иерархическая нумерация вида `S4:2:1` [METHOD: P0172].

## Потоки ошибок

Идентификатор: `E<n> [условие]`.

Поток ошибок описывает исключительную ситуацию, не относящуюся к нормальному развитию процесса [METHOD: P0173–P0174].

## Связь с UML

Если в текстовом потоке появляется безусловный подпоток `S...`, соответствующая Use Case dependency должна быть кандидатом на `include`.

Если подпоток выполняется только по условию, это кандидат на `extend`, а условие должно совпадать по смыслу с `UMLExtend.Condition`.

Таким образом текстовый поток и графическая диаграмма должны проверять друг друга.
