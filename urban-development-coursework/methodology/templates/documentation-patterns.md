# Шаблоны Documentation

Это не готовый текст для копирования без проверки, а структура обоснования элементов.

## Actor

Указать:

- почему сущность находится вне моделируемой системы;
- какую функциональность она потребляет или предоставляет;
- какие Use Case инициирует/в каких участвует.

Основание: [METHOD: P0073].

## worker

Указать:

- почему человек считается внутренней частью системы;
- какую часть функциональности выполняет;
- почему используется стереотип `worker`.

Основание: [METHOD: P0121–P0135].

## Use Case

Указать:

- цель функции;
- входные условия/данные на смысловом уровне;
- результат;
- границу ответственности;
- связь с текстовым потоком.

Название должно описывать процесс [METHOD: P0092].

## Association Actor → Use Case

Обосновать, является ли Association направленной или ненаправленной, исходя из роли Actor в взаимодействии [METHOD: P0155–P0158].

## include

Шаблон смысла:

«При реализации <base> функциональность <included> используется безусловно, поэтому выбрано отношение include».

Основание: [METHOD: P0159–P0160].

## extend

Шаблон смысла:

«При реализации <base> функциональность <extension> используется только при условии <condition>, поэтому выбрано отношение extend».

То же условие должно быть записано в property `Condition` [METHOD: P0161–P0163].

## Activity Action / Activity

Пояснение должно устранять неоднозначность названия и доводить смысл до уровня, достаточного для реализации [METHOD: P0251–P0254].

## Activity Transition

Обосновать набор `Trigger / Guard Condition / Effect` [METHOD: P0256].

## Class member

Для детального Class View документировать назначение атрибута/операции, access modifier и типы [METHOD: P0408–P0409].

## Class relation

Обосновывать семантику конкретного отношения, особенно aggregation/composition/dependency [METHOD: P0410; P0415–P0419; P0426–P0438].
