# 3. Модель классов

## Откуда должны появляться классы

Методичка связывает классы со всеми аспектами модели: операции выражают функциональность, атрибуты — информацию, объекты классов участвуют в Interaction Diagram, а совокупность классов участвует в модели структуры системы [METHOD: P0353–P0354].

Class Diagram рекомендуется строить на основе поведенческих моделей — текстовых потоков Use Case, Activity, State Machine, Sequence/Communication [METHOD: P0355].

Действия системы из Activity Diagram при переходе к Class Model превращаются в операции классов [METHOD: P0355–P0357; P0378].

## Выделение классов

Методичка показывает учебный переход от обобщённого класса «Система» к набору классов трёх типов [METHOD: P0359–P0374]:

- `boundary` — граница/интерфейс взаимодействия;
- `control` — управление последовательностью и прикладной логикой;
- `entity` — информационные сущности.

Ориентировочный принцип: ActionState может приводить к выделению класса, реализующего действие [METHOD: P0378–P0380].

Для State Machine аналогичный ориентир: простому State может соответствовать класс [METHOD: P0385–P0386].

Это **не механическое правило один Action = один Class**: методичка прямо допускает объединение группы действий в один класс [METHOD: P0380].

## Пакеты

Классы следует разделять на пакеты сущностей, граничных и управляющих классов [METHOD: P0405].

Это хорошо объясняет пакеты `Boundary`, `Control`, `Entity` в `lending.uml`.

## Три обязательных представления Class Model

Методичка требует представлять Class Diagram в трёх видах [METHOD: P0406–P0410].

### 1. Package view

Диаграмма пакетов с вложенными классами; классы могут быть показаны кратко, только именами [METHOD: P0407].

### 2. Detail view

Детальное представление классов. Обязательно указываются все атрибуты и операции, access specifiers, типы атрибутов, типы параметров и возвращаемых значений; члены класса должны быть задокументированы [METHOD: P0408–P0409].

### 3. Relations view

Диаграмма отношений между классами. Детальность самих классов может отличаться, но главное — подробное документирование отношений [METHOD: P0410].

Это прямо соответствует сериям `...Packages`, `...DetailClass`, `...DetailClassWithRelation` в `lending.uml`.

## Логическая целостность

Все классы, отображённые в Package Diagram, должны затем появиться в детальных диаграммах [METHOD: P0450–P0452].

Это будет отдельной автоматической проверкой registry.

## Отношения

Association/aggregation/composition методичка трактует как отношения по данным [METHOD: P0412–P0415].

Aggregation и composition различаются жизненным циклом частей: при aggregation часть продолжает существовать без целого, при composition уничтожается вместе с целым [METHOD: P0415–P0419].

Dependency применяется, в частности:

- между процедурными классами при вызове методов — `call` [METHOD: P0426–P0428];
- между процедурным классом и entity при использовании его данных — `use` [METHOD: P0429–P0430];
- для создания объектов — `instantiate/create` [METHOD: P0431–P0438].

## Для Urban Development

Классы не следует автоматически копировать из Python-кода. Сначала фиксируем действия/состояния в поведенческой модели, затем выделяем boundary/control/entity классы и сверяем их с реальной архитектурой.

Сильные кандидаты entity: `Project`, `Dataset`, `DatasetVersion`, `GenerationRun`, `RunStageResult`, `Artifact`, generated/source spatial entities.

Control-классы должны следовать из прикладных сценариев, а boundary — из реальных UI/API boundaries.
