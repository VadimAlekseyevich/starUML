# 3. Модель классов

## Откуда появляются классы

Методичка связывает Class Model с предыдущими этапами: операции выражают функциональность, атрибуты — информацию, объекты участвуют во взаимодействиях [METHOD: P0353–P0354].

Class Diagram строится на основе Use Case flows, Activity, State Machine и Sequence/Communication [METHOD: P0355].

Действия системы становятся обязанностями/операциями классов [METHOD: P0355–P0357; P0378].

## Boundary / Control / Entity

Методичка предлагает три аналитических типа [METHOD: P0359–P0374]:

- `boundary` — взаимодействие с внешней средой/пользователем;
- `control` — управление сценарием и прикладной логикой;
- `entity` — предметные данные.

Это правило сохраняется в StarUML 7 без привязки к внутренним XPD-классам.

## Не делать механически

ActionState может подсказать класс, но правило «один Action = один Class» неверно; группа действий может реализовываться одним классом [METHOD: P0378–P0380].

То же относится к State [METHOD: P0385–P0386].

## Пакеты

Классы группируются в entity/boundary/control packages [METHOD: P0405].

Для Urban Development дополнительно можно группировать по предметным областям, если это не разрушает эту аналитическую классификацию:

- project;
- geodata;
- scenario;
- generation;
- metrics;
- export.

## Три обязательных представления

Методичка требует [METHOD: P0406–P0410]:

1. **Package view** — классы и пакеты, допускается сокращённое представление.
2. **Detail view** — все атрибуты/операции, visibility, types, parameters, result types, Documentation.
3. **Relations view** — отношения между классами с пояснениями.

Тройки `...Packages / ...DetailClass / ...DetailClassWithRelation` в lending — хороший старый пример реализации этого требования, но имена и XPD-структуру копировать не нужно.

## Отношения

Aggregation/composition различаются жизненным циклом части [METHOD: P0415–P0419].

Dependencies `call/use/instantiate/create` выбираются по реальному использованию [METHOD: P0426–P0438].

## Логическая целостность

Каждый класс Package view должен существовать в Detail view [METHOD: P0450–P0452].

Следующий MDJ-validator должен уметь проверять это по `_id`.
