# Interaction diagrams: Sequence / Communication

## Назначение

Sequence Diagram является альтернативным средством моделирования поведения и одновременно показывает алгоритм через сообщения и структуру через объекты-обработчики [METHOD: P0476].

Sequence и Communication семантически рассматриваются как эквивалентные формы взаимодействия [METHOD: P0458–P0460].

## Место в порядке проектирования

Для построения Sequence Diagram методичка рекомендует предварительно выделить классы; для этого полезны Activity или State Machine Diagram [METHOD: P0478–P0485].

Для простого алгоритма допускается обратный путь, когда Sequence помогает выявить классы [METHOD: P0486–P0489].

Наш базовый порядок:

`Use Case → Activity/State Machine → Class → Sequence`.

## Messages и операции классов

При создании сообщения на Sequence Diagram его имя должно соответствовать операции класса-получателя [METHOD: P0496–P0501].

Методичка подчёркивает: надписи над сплошными стрелками — вызовы операций тех классов, в чьи lifeline входит стрелка; такие операции обязательно должны присутствовать в Class Model [METHOD: P0501].

Это становится важным правилом автоматической трассировки Class ↔ Sequence.

## Combined Fragment

Методичка перечисляет `alt`, `opt`, `loop`, `strict`, `par`, `seq` и их смысл [METHOD: P0461–P0470].

Условное выполнение одного блока выражается `opt`; ветвление на варианты — `alt` [METHOD: P0464–P0467; P0506–P0507].

## Создание объектов

Объект, создаваемый в ходе сценария, должен появляться на диаграмме на уровне вызова конструктора/сообщения `create`, а не в верхнем ряду объектов, существовавших до начала сценария [METHOD: P0508–P0509].

## Controller

В примере методички Controller задаёт порядок выполнения операций других объектов и формирует сценарий [METHOD: P0510].

Для Urban Development это хорошо согласуется с control/application-service слоем, но конкретное имя класса будет определяться нашей Class Model, а не копироваться из примера.
