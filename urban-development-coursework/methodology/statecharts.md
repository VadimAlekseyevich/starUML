# Диаграмма автомата / State Machine

## Назначение по методичке

State Machine определяется как совокупность состояний и переходов между ними [METHOD: P0279–P0283].

Методичка рассматривает State Machine Diagram как альтернативную форму алгоритмической реализации конкретного сценария/Use Case, а не как самостоятельную декоративную схему [METHOD: P0286–P0287].

## Поакторная модель

Разработку сценариев автомата рекомендуется вести по Actor: сначала сценарий использования системы первым Actor, затем вторым и т. д. [METHOD: P0288–P0289].

Если Actor связан с несколькими Use Case, укрупнённый сценарий должен включать выбор необходимого варианта использования [METHOD: P0291–P0293].

После этого выполняется алгоритмическая реализация самих Use Case и при необходимости вспомогательных прецедентов [METHOD: P0294–P0298].

## Иерархия

Принцип основной/декомпозиционной модели здесь аналогичен Use Case и Activity [METHOD: P0291].

Сложный сценарий сначала отображается укрупнённо, а затем нетривиальные состояния/подпроцессы детализируются отдельными автоматами или деятельностями [METHOD: P0294–P0297].

## Для Urban Development

State Machine имеет смысл использовать там, где алгоритм естественно выражается устойчивыми состояниями:

- жизненный цикл `GenerationRun`;
- жизненный цикл `Job`;
- жизненный цикл `DatasetVersion`.

Однако это должно быть связано с реализацией конкретного сценария/Use Case. Не следует строить State Machine исключительно потому, что в `lending.uml` их четыре.
