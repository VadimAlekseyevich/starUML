# 1. Модель функциональности

## Что именно требуется

Методичка прямо определяет Use Case как функцию/задачу/работу, реализуемую процессом [METHOD: P0063–P0066], а диаграмму вариантов использования — как средство моделирования функциональности программно-информационной системы [METHOD: P0098].

Это подтверждает рабочую трактовку первого пункта `Порядок.txt`:

**модель функциональности = основная диаграмма прецедентов + декомпозиционные диаграммы + текстовые сценарии/потоки.**

## Именование Use Case

Название прецедента должно быть названием процесса, а не названием данных, результата, события или условия [METHOD: P0092].

Для Urban Development хорошие формы:

- «Создать проект»;
- «Настроить сценарий развития»;
- «Выполнить генерацию сценария»;
- «Сравнить сценарии».

Плохие формы:

- «Результаты генерации»;
- «Проект создан»;
- «Ошибка данных».

## Actor и worker

Actor — внешняя по отношению к моделируемой системе сущность [METHOD: P0073].

Если человек является **частью системы** и выполняет часть её функциональности, он не Actor, а worker [METHOD: P0121–P0124]. Для StarUML 5 методичка предлагает создавать Class и назначать ему стереотип `worker` [METHOD: P0125–P0135].

Это объясняет структуру `lending.uml`, где «Менеджер» хранится как `UMLClass`, а не `UMLActor`.

Следовательно, текущий `ГИС-аналитик` в Urban Development как класс/worker концептуально корректен, если мы считаем его штатным участником проектируемой системы.

## Отношения

Между Actor и Use Case используется Association [METHOD: P0080–P0082].

Между Use Case допустимы include, extend и generalization; Association между Use Case методичка отдельно запрещает [METHOD: P0078–P0082].

`include` означает безусловное использование функциональности включаемого прецедента [METHOD: P0083–P0085].

`extend` означает использование дополнительной функциональности только при условии [METHOD: P0084–P0085].

Для `extend` условие обязательно должно быть записано в property `Condition` стрелки [METHOD: P0161–P0163].

## Основная диаграмма

Use Case Model должна состоять из нескольких диаграмм: одной основной и декомпозиционных [METHOD: P0102–P0103].

На основной диаграмме рекомендуется показывать относительно независимые варианты использования. В учебном проекте их обычно 3–9 [METHOD: P0104].

Методичка рекомендует **не выполнять даже частичную декомпозицию на основной диаграмме**; при хорошем выделении верхнеуровневых Use Case зависимости между ними обычно отсутствуют [METHOD: P0105].

Информационные связи между независимыми функциями при необходимости лучше пояснять Note/NoteLink, а не превращать их в ложные функциональные зависимости [METHOD: P0105–P0106].

Интерфейсные/технические вспомогательные функции допустимо скрывать, чтобы не перегружать основную диаграмму [METHOD: P0107].

## Декомпозиционная диаграмма

Декомпозиционная диаграмма должна содержать сам декомпозируемый Use Case как логический центр; остальные прецеденты связываются с ним зависимостями [METHOD: P0112].

Методичка требует построить декомпозиционные диаграммы вариантов использования, представленных на диаграмме первого уровня [METHOD: P0138–P0141].

## Текстовые сценарии и потоки

Для каждого базисного варианта использования основной диаграммы обязательно создаётся описание потока поведения [METHOD: P0099].

Также требуется составить сценарий использования системы каждым Actor [METHOD: P0108–P0109; P0143–P0145].

Все Use Case должны иметь текстовый алгоритм реализации в прикреплённом документе/Attachment [METHOD: P0164].

Методичка задаёт структуру потоков:

- основной поток;
- альтернативные потоки `A...` с условиями;
- подпотоки `S...`;
- потоки ошибок `E...` [METHOD: P0165–P0174].

Примеры форм находятся в таблицах T0002–T0004.

## Documentation

Все узлы и стрелки диаграмм должны иметь пояснения в `Documentation` [METHOD: P0149–P0153].

Для Association пояснение должно обосновывать направление/ненаправленность [METHOD: P0155–P0158].

Для include/extend пояснение должно обосновывать, почему функциональность используется безусловно либо по условию [METHOD: P0159–P0163].

## Критерий завершённости этапа

Этап функциональности нельзя считать завершённым только потому, что картинки построены. Нужны согласованные имена/GUID, декомпозиции верхнеуровневых Use Case, реальные Condition для extend, Documentation элементов и текстовые потоки/сценарии.
