## Что не устраивало в предыдущем представлении

1. Вторая работа выглядела иначе, чем импортированная первая: стандартное оформление и Arial 13 вместо бордово-кремовой палитры эталонного курсача.
2. Избыточно высокие полотна (наибольшее около 3000 px) и ряд с шагом 135 px.
3. Часть labels имела X за пределами рабочих дорожек (`-230`, `1000` при ширине дорожек до `960`) и не находилась рядом с ветвью Decision.
4. Некоторые переходы физически шли через чужие Action/control nodes; показательный пример — альтернативный выход `ScenarioLaunch` в общий конечный узел сквозь центральный конвейер.
5. На диаграммах не было компактного видимого пояснения входа/выхода, хотя оно есть в Documentation.
6. Шаги `GenerationExecution` отображались как машинные идентификаторы, хотя смысл этапов гораздо яснее формулируется глаголами на русском.
7. Текст описания запуска мог читаться как блокирующий синхронный вызов Worker, хотя Worker — самостоятельная фоновая задача.

## Что изменено в MDJ

- Всем десяти Activity и дополнительной State Machine задан единый визуальный язык, совместимый с первой работой: `lineColor #800000`, `fillColor #FFFFB9`, Arial 11.
- Добавлены десять notes с предметными входами и выходами и визуальной ссылкой на initial node.
- Вертикальный шаг действий сокращён примерно до 116 px; действия остались 320×72 px, минимальный промежуток между ними — не менее 40 px.
- Guards размещены в свободном пространстве рядом с Decision, с переносом длинного текста.
- Маршруты стрелок, пересекавшие посторонние Action/Control Node, перестроены через свободные проходы; существующие `UMLControlFlow`, source/target и `_id` сохранены (кроме осознанного изменения target для альтернативного Activity Final).
- В `ScenarioLaunch`, `DatasetImport`, `ResultExport`, `GenerationExecution` исходы ошибок, отмены и успеха заканчиваются собственными Activity Final. Они больше не идут одним длинным маршрутом через все следующие действия. Этим конечным узлам выданы новые уникальные ID.
- Англоязычные ключи pipeline оставлены в Documentation каждого этапа, отображаемые имена стали процессными русскими фразами. Порядок двенадцати шагов не менялся.
- State Machine сжата по ширине. Пояснение и Documentation отличают предварительную подготовку конфигурации Draft/Validated от существующего Run с состояния Queued.
- Документирован асинхронный Worker: `CallBehaviorAction` представляет UML-связь поведения, а не блокирующий HTTP-вызов.
- Устранено повторение metrics/manifest в текстовом основном потоке `flows/UC_GenerationExecution.txt`.

## Требования методички, которые сохраняем

- `P0220`, `P0225`, `P0242–P0246`: диаграмма реализации каждого Use Case первого уровня плюс оправданные декомпозиции.
- `P0191–P0196`, `P0255`: для нетривиальных поддеятельностей сохраняем прямые вызовы `UMLCallBehaviorAction → UMLActivity`.
- `P0227–P0229`: предметные guards и единственная резервная ветвь `[else]`.
- `P0234–P0239`: логические действия пользователя и реакция системы в отдельных swimlanes; технические Frontend/API/Worker не множатся без причины.
- `P0251–P0256`: содержательная Documentation узлов/стрелок.
- `P0274–P0275`: альтернативные входы Action сливаются до действия через Merge.
- Fork/Join **не добавлены ради внешнего подражания**: они применимы лишь там, где предметная логика допускает действительную параллельность.

## Проверка

Структурный проход по изменённому MDJ установил уникальность всех `_id`, разрешимость всех `$ref`, отсутствие попадания проложенных стрелок на посторонние узлы. Проверку `audit_staruml7.py` дополнительно расширили анализом таких пересечений, чтобы последующие правки не вернули исходный дефект. Полнота Activities и traceability не менялась.

**Ограничение:** геометрический аудит выполняется по координатам MDJ; это не пиксельное сравнение экспорта из установленного StarUML 7. Для финального отчёта преподавателю нужно открыть изменённый файл в StarUML и экспортировать диаграммы; убедиться, что конкретная версия редактора не обрезает notes, guards и текст в узлах. Пересоздавать модель в старом XPD ради этого не нужно.
