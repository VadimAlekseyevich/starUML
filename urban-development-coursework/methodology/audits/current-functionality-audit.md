# Аудит текущей модели функциональности

Объект аудита: `dist/urban_development.uml`.

Дата базовой проверки: 2026-09-22.

## Что уже соответствует методичке

### Модель состоит из нескольких Use Case Diagram

Есть одна обзорная диаграмма `UrbanDevelopment` и пять детальных диаграмм. Это соответствует принципу «основная + декомпозиционные» [METHOD: P0102–P0103].

### Количество Use Case на обзорной диаграмме

На `UrbanDevelopment` отображено 6 Use Case, что попадает в типичный диапазон 3–9 для учебной основной диаграммы [METHOD: P0104].

### Внутренний специалист представлен классом

`ГИС-аналитик` хранится как `UMLClass`, а не Actor. Это соответствует правилу о внутреннем работнике системы — `worker` [METHOD: P0121–P0135].

### Существует декомпозиция ключевых функций

`Создать проект`, `Управление исходными геоданными`, `Настроить сценарий развития` уже имеют отдельные диаграммы, в которых базовый Use Case присутствует как логический центр. Это соответствует [METHOD: P0112].

## Что требует исправления перед завершением функциональной модели

### 1. Основная диаграмма сейчас частично декомпозирована

`UrbanDevelopment` содержит один `UMLExtendView`. Методичка рекомендует не выполнять частичную декомпозицию на основной диаграмме и обычно не связывать верхнеуровневые варианты использования зависимостями [METHOD: P0105].

Нужно проверить, действительно ли `Просмотреть выбранный сценарий` должен быть на основной диаграмме. Скорее всего это вспомогательный Use Case декомпозиции `Просмотр и сравнение сценариев`.

### 2. На основной диаграмме присутствуют вспомогательные функции

Сейчас на обзорной схеме отображаются:

- `Просмотреть слои и исходные данные`;
- `Просмотреть выбранный сценарий`.

По смыслу это более детальные операции. Методичка рекомендует скрывать технические/вспомогательные функции с основной диаграммы [METHOD: P0107].

Рабочее решение: перенести их на соответствующие декомпозиционные диаграммы, если после семантического пересмотра они действительно являются вспомогательными.

### 3. Нет отдельной декомпозиции «Просмотр и сравнение сценариев»

`Просмотр и сравнение сценариев` находится на основной диаграмме, но отдельной Use Case Diagram для него пока нет.

Методичка требует строить декомпозиции вариантов использования первого уровня [METHOD: P0138–P0141].

Нужно добавить диаграмму, условное рабочее имя: `ScenarioComparison`.

### 4. Нужно решить статус «Запустить сценарий развития»

Сейчас `ScenarioLaunch` существует как дальнейшая декомпозиция `ScenarioConfiguration`, но `Запустить сценарий развития` не показан как отдельный верхнеуровневый Use Case.

Нужно предметно решить, является ли запуск самостоятельной относительно независимой функцией основной диаграммы или обязательной частью настройки/выполнения сценария. Решение должно исходить из пользовательского сценария, а не из структуры lending.

### 5. Documentation отсутствует

В текущем UML-файле найдено:

- `Documentation` attributes: **0**.

Методичка требует документировать все узлы и стрелки [METHOD: P0142; P0149–P0163].

При создании первой версии банковские Documentation были намеренно удалены, чтобы не оставить ложную семантику. Теперь их нужно заполнить заново уже по Urban Development.

### 6. Condition у extend пока временные

Найдено 14 properties `Condition`, и все 14 содержат временную фразу:

`Выполнение дополнительного условия сценария`.

Методичка требует конкретную формулировку условия extend непосредственно в property `Condition` [METHOD: P0161–P0163].

Все 14 условий необходимо заменить предметными условиями.

### 7. Текстовые потоки и Attachments отсутствуют

В текущем UML:

- `Attachments` attributes: **0**.

Для базовых Use Case нужны потоки поведения [METHOD: P0099], для всех Use Case — текстовые алгоритмы реализации [METHOD: P0164], а сценарии Actor должны быть связаны с моделью [METHOD: P0143–P0145].

Нужно создать текстовые спецификации потоков и решить, каким способом хранить attachment references в собираемом StarUML-проекте без workstation-specific путей.

## Приоритет исправлений

Сначала привести в соответствие **семантику основной диаграммы**, потому что именно она определяет обязательный набор декомпозиционных Use Case и последующих Activity/State Machine Diagram [METHOD: P0220; P0225].

Только после этого массово добавлять Documentation, Conditions и текстовые потоки — иначе придётся документировать элементы, которые затем будут перемещены/переименованы.
