## Что показала методичка

### Обязательное покрытие

[P0220], [P0225], [P0242] требуют Activity Diagram для каждого Use Case основной диаграммы. Это покрытие было и остаётся 6/6.

### Декомпозиция

[P0193–P0196], [P0225], [P0246], [P0255] требуют выделять отдельную деятельность, когда внутренний алгоритм неочевиден и ссылка на него используется из более крупного алгоритма.

После ревизии выделены:

- `DatasetImport`;
- `DataQualityValidation`;
- `ScenarioValidation`;
- `GenerationExecution`.

В StarUML 7 вызовы представлены `UMLCallBehaviorAction` и ссылаются на `UMLActivity.behavior`. Это семантически соответствует `SubactivityState` из старой версии.

### Один вход в Action

[P0274] прямо требует один вход в Action. В предыдущей версии модели нашлись реальные нарушения: повторный ввод/выбор сходился непосредственно в Action. Исправлено с помощью merge-узлов в `ProjectCreation`, `DataManagement`, `ScenarioConfiguration`, `ScenarioComparison`, `ResultExport`.

### Guards

[P0227–P0229] рекомендуют содержательные guard и `else`, а не «Да/Нет». Парные отрицательные подписи заменены на `[else]` там, где это резервная ветвь.

### Documentation

[P0251–P0256] требуют документировать все узлы и стрелки и устранять неполноту названий. Предыдущие пояснения были формально заполнены, но часто повторяли название шага. Теперь для действий описываются входы, проверка, изменение состояния/данных и выход; для стрелок — причина безусловного перехода либо смысл guard.

## Что показал lending.uml

Полная модель содержит:

| Тип | Количество |
|---|---:|
| Use Case | 8 |
| Activity | 5 |
| Statechart | 4 |
| Class | 13 |
| Component | 8 |
| Deployment | 2 |
| Sequence | 1 |

Activity `ApplyingForLoan` особенно полезна как образец масштаба:

- 3 swimlane;
- 12 Action/Subactivity;
- 2 SubactivityState;
- 13 псевдосостояний;
- 32 перехода;
- полотно примерно 900 px по ширине рабочих дорожек и более 1300 px по высоте.

Остальные Activity имеют примерно 5–9 действий и 15–19 переходов. Это показывает, что хороший курсовой пример сочетает основную диаграмму с несколькими **обоснованными** поддеятельностями, но не дробит каждый элемент в отдельную диаграмму.

Statechart в lending имеют от 3 до 9 состояний и примерно 10–23 перехода. Текущий `GenerationRunLifecycle` (7 предметных состояний плюс initial, 9 переходов) находится в разумном диапазоне и имеет самостоятельный смысл жизненного цикла. Добавлять автоматы только ради количества не требуется.

## Что изменено после аудита

1. Добавлены `DatasetImport`, `DataQualityValidation`, `ScenarioValidation`.
2. Вызовы сложных деятельностей оформлены как `UMLCallBehaviorAction`.
3. Исправлены входы Action через merge.
4. Резервные guard приведены к `[else]`.
5. Documentation расширена.
6. Основные Activity переразложены с большим количеством свободного места.
7. Обратные переходы маршрутизируются снаружи основной колонки.
8. State Machine разнесена по более широкому полотну.
9. В validator добавляются проверки этих инвариантов.

## Что сознательно НЕ добавлено

- отдельные Activity для каждого простого действия;
- автоматы для сущностей без самостоятельного жизненного цикла;
- legacy `ActivityGraph/TOP` и другие внутренние конструкции StarUML 5;
- параллельные fork/join без реальной параллельности процесса;
- технические Frontend/API/DB дорожки там, где достаточно уровня «Пользователь / Система».

Это не сокращение ради простоты, а остановка декомпозиции там, где дальнейшее дробление уже не добавляет проектного смысла [METHOD: P0298].

## Инструкция следующему чату

Перед изменением работы 2:

1. Читать этот файл и `../algorithms.md`.
2. Канонический файл — единственный `.mdj` в `01_functionality/`.
3. Не создавать второй `.mdj`.
4. Сохранять существующие `_id` семантических элементов.
5. Для сложной повторно используемой работы предпочитать `UMLCallBehaviorAction → UMLActivity`, а не копировать алгоритм.
6. Не направлять несколько control flow прямо в Action; сначала merge.
7. Для Decision использовать guard и `[else]`.
8. Documentation должна отвечать «что входит / что проверяется / что меняется / что выходит».
9. При визуальной правке оставлять запас пространства; плотность не является достоинством.
10. После изменения запускать `scripts/audit_staruml7.py`.
