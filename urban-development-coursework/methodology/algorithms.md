# 2. Модель алгоритмов

## Роль поведенческих диаграмм

Методичка определяет поведение ИС как совокупность процессов [METHOD: P0180–P0183].

Основными средствами моделирования поведения названы State Machine, Activity, Sequence и Communication Diagram [METHOD: P0184–P0189].

Для нашей второй части основной рабочий инструмент — Activity Diagram; State Machine используется как альтернативная форма алгоритмической реализации там, где это уместно.

## Связь с Use Case

Поведенческие диаграммы представляют алгоритмические реализации Use Case [METHOD: P0219].

Для **каждого варианта использования основной диаграммы** должна быть создана поведенческая диаграмма [METHOD: P0220].

Для Activity Diagram требование повторено отдельно: они строятся для каждого Use Case первого уровня [METHOD: P0225; P0241–P0245].

Следовательно, окончательный набор Activity/State Machine нельзя проектировать независимо от основной Use Case Diagram.

## ActivityGraph и размещение

Диаграммы деятельности следует помещать в `Logical View` [METHOD: P0201].

Для StarUML 5 методичка описывает контейнер `ActivityGraph`, внутри которого находится `TOP`, объединяющий элементы диаграмм [METHOD: P0202–P0206].

Это полностью совпадает с реальным устройством `lending.uml`.

## ActionState и SubactivityState

`ActionState` используется для действия или деятельности, алгоритм которой уже понятен читателю [METHOD: P0191–P0194].

`SubactivityState` используется как ссылка на деятельность с неизвестным/отдельно описываемым алгоритмом; для такой деятельности создаётся дополнительная диаграмма реализации [METHOD: P0193–P0196].

Каждая содержательно нетривиальная ссылка SubactivityState должна иметь собственную Activity Diagram [METHOD: P0255].

## Имена

Имя Activity Diagram может совпадать с именем деятельности; для самих диаграмм методичка рекомендует английские имена из-за инструментальных ограничений [METHOD: P0216–P0217].

Наше рабочее соглашение: внутреннее имя диаграммы — стабильный ASCII/English identifier, а русская семантика фиксируется в Documentation/подрисуночной подписи и registry.

## Ветвления

Над выходами Decision **не надо писать «Да/Нет»**. Нужно указывать реальные guard conditions, а для остаточной ветви рекомендуется `else` [METHOD: P0227–P0229].

Guard задаётся в свойствах стрелки `GuardCondition/Condition/Guard`, чтобы отображаться в квадратных скобках [METHOD: P0229].

Decision используется и для ветвления, и для слияния потоков [METHOD: P0229; P0274–P0275].

## Swimlanes

При использовании дорожек для людей указывается логический смысл действия человека, а не физические клики мышкой/клавиатурой [METHOD: P0234–P0236].

Допустимо объединить клиентскую и серверную части в дорожку «Система», если текущий уровень моделирования не требует технической детализации [METHOD: P0239].

Для Urban Development гранулярность дорожек выбирается по контексту. На алгоритмическом уровне разумны, например, `Пользователь`, `Система`, а на архитектурно-техническом — `Frontend`, `Backend`, `Worker/Core`.

## Documentation

Все узлы и стрелки Activity Diagram должны иметь Documentation [METHOD: P0251].

Пояснение Action/Activity должно устранять неоднозначность и быть достаточно точным для будущей программной реализации [METHOD: P0252–P0254].

Пояснение перехода должно обосновывать Triggers, Guard Condition и Effects [METHOD: P0256].

## Первые кандидаты Urban Development

После корректировки основной Use Case Diagram каждому её верхнеуровневому Use Case будет сопоставлена поведенческая реализация.

Уже очевидные содержательные процессы:

- создание/подготовка проекта;
- управление исходными геоданными;
- настройка сценария развития;
- запуск и выполнение генерации;
- просмотр/сравнение сценариев.

Точная декомпозиция должна следовать от окончательной основной Use Case Diagram, а не наоборот.
