# Urban Development Coursework — UML workspace

Эта папка — рабочая система курсового проекта по дисциплине «Проектирование информационных систем».

## Текущий рабочий формат

После успешной миграции проект разрабатывается в **StarUML 7**. Канонический редактируемый файл:

`01_functionality/urban_development_functionality.mdj`

Именно `.mdj` открываем, редактируем и развиваем на следующих этапах.

Старые `.uml`, XPD fragments и XPD-валидаторы сохранены как **legacy-слой**: они нужны для истории, воспроизводимости миграции и чтения эталонного `lending.uml`, но больше не являются рабочим способом построения курсача.

Подробный процесс: [STARUML7_WORKFLOW.md](./STARUML7_WORKFLOW.md).

## Приоритет источников

Если источники расходятся:

1. **Методические указания** — что требуется семантически.
2. **`lending.uml` и `Костыль/`** — как похожая работа была оформлена на практике.
3. **`urban-development-generator`** — реальные процессы, сущности и архитектура нашей системы.
4. Общие правила UML.
5. Особенности конкретной версии StarUML — только технический способ выразить выбранную UML-семантику.

## Что берём из старого примера

Берём:

- набор и назначение диаграмм;
- уровень декомпозиции;
- UML-отношения;
- Documentation;
- boundary/control/entity;
- package/detail/relations;
- визуальные приёмы;
- связь этапов курсача.

Не считаем обязательным:

- XPD/XML;
- `XPD:REF`;
- `#OwnedElements`;
- внутренние `*View` StarUML 5;
- ручную сборку XML;
- случайные особенности дерева старого файла, если они не подтверждены методичкой.

## Структура

- `01_functionality/` — первая работа и текущий `.mdj`;
- `flows/` — текстовые сценарии Use Case;
- `methodology/` — наши правила, выведенные из методички;
- `reference/` — старый lending, Костыль, изображения и legacy XML как образцы;
- `model/` — трассировка, канонические имена и cross-diagram contract;
- `fragments/`, `dist/` — legacy StarUML 5/XPD;
- `scripts/` — extractors и legacy-проверки.

## Главное правило согласованности

**Один предметный элемент = один model element = один стабильный `_id` в `.mdj`.**

Если один Use Case, класс или компонент появляется на нескольких диаграммах, показываем один и тот же model element через несколько View, а не создаём дубликаты.

При импорте StarUML 7 сохранил старые GUID как `_id`, поэтому идентичность элементов первой работы сохранилась.

## Рабочий процесс

1. Выбрать этап по `Порядок.txt`.
2. Прочитать соответствующий раздел `methodology/`.
3. Посмотреть эталон в `reference/` и `Костыль/`.
4. Проверить реальные процессы в `urban-development-generator`.
5. Создать/изменить диаграмму непосредственно в StarUML 7.
6. Проверить трассировку с предыдущим этапом через `model/`.
7. Визуально проверить диаграмму.
8. Закоммитить `.mdj` и связанную документацию.
